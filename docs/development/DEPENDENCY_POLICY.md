# Dependency graphs and release provenance

## Canonical release graph

The canonical release graph is the frozen `pnpm-lock.yaml` installed with the exact `packageManager` version in `package.json` (currently pnpm 10.30.2). Docker builds use this graph. `package-lock.json` is a supported npm compatibility graph; npm is included with the supported Node runtime and does not require installing pnpm.

Both graphs must declare identical direct dependencies. Transitive version sets may differ only as explicitly recorded in [the difference ledger](../../config/lockfile-differences.json). The initial ledger records the existing graphs, without silently resolving or upgrading packages: 31 package-name differences, principally Rolldown/native bindings, Markdown parsers and build/test utilities. An absent package is represented by an empty version list. This corrects the historical approximate count of 30; it does not establish that either graph is defective or interchangeable.

The ledger is a review boundary, not a blanket approval of future versions. `npm run locks:check` rejects unrecorded differences, a mismatched canonical manager and npm root-metadata drift. pnpm's frozen install checks importer consistency. Identical version sets do not prove identical dependency edges; reviewers must inspect lockfile changes as well as the ledger.

## Dependency updates

Use Node >=24.11.0 <25. Change direct dependency declarations and regenerate both locks in one focused dependency PR using the pinned pnpm and a recorded npm version. Inspect resolution, integrity and engine changes in both files; update the ledger only after reviewing each changed difference. Do not copy checksums or versions between lock formats to manufacture parity. Commit changed locks together and explain any graph that remains byte-identical after regeneration in the PR.

Run fresh `npm ci` and `pnpm install --frozen-lockfile` in separate disposable checkouts. Each graph must pass full verification, formatting and browser tests. Never install one manager over the other's existing dependency tree and call that fresh acceptance. Release evidence comes from the eight Linux/Windows, npm/pnpm and minimum/current-Node matrix legs in the shared acceptance workflow.

## Parity and evidence

After verification and browser tests, every leg records source revision, runtime, manager identity, both lockfile hashes, generated catalog/feed hashes and a rendered GFM corpus hash. The corpus exercises tables, task lists, links, fenced code and unsafe HTML because Markdown parser versions currently differ. Static bundles can have different names/bytes under the two bundler graphs; production-artifact checks and browser journeys must pass independently for each graph. Byte-identical bundles are not claimed.

The parity job requires all eight records from the same source revision and the same lockfile pair. It fails on missing/duplicate evidence, changed generated bytes or changed Markdown rendering. The aggregate release gate requires parity as well as the full matrix and containers. Provenance is uploaded as CI artifacts; consult it for actual npm/Node versions rather than inferring them from a local installation.

For a local diagnostic, run `node scripts/verification-provenance.mjs <output-path>` after building under one clean graph. CI supplies the source/matrix labels; local output without those labels is not release evidence. `node scripts/verification-provenance.mjs --compare <downloaded-evidence-directory>` verifies a complete downloaded acceptance set.
